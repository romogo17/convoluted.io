PATs are the obvious starting point. GitHub surfaces them first, every CI system knows how to use them, and they work well, right up until they don't. The fragility is structural: a PAT is always tied to a person, which means you're one password reset, one 2FA policy rollout, or one offboarding away from a 2am incident where nobody remembers which account the token belongs to.

So what's the alternative? A GitHub App is a different kind of account. You register it once and GitHub treats it as its own actor. Not a human, not a service user wearing a human's face. It has a name, a private key it signs with, a set of permissions you declare up front, and its own line in the audit log as `your-app[bot]`. You install it onto the orgs or repositories that need it, and from then on it authenticates as itself.

The payoff is that everything it hands out is short-lived and scoped to a single installation. No shared password to rotate, nobody to offboard, no 2am guessing game about whose account a token belongs to. The mental-model shift from a PAT is small. The operational improvement is not.

This guide builds that model piece by piece: what an app is made of, the two ways it can authenticate, and the tokens each flow produces. Read it start to finish to understand the system, then keep it around as the reference you come back to.

## The anatomy of a GitHub App

A handful of ideas make up the whole model: what the app is, where it lives, what it's allowed to do, and the one optional secret. Get these straight and the auth flows follow naturally.

### App vs installation

The **App** is the definition: its name, keys, and declared permissions. An **Installation** is the App installed on a specific enterprise, org, or user account. Permissions live on the installation, not the app. When an admin installs your app and grants it `Enterprise teams (read)`, that grant attaches to the installation record. The app has no access to anything until it's installed somewhere.

### The three identifiers

An app carries three IDs, and mixing them up is the most common source of confusion:

- **App ID** identifies what the app is. It's numeric, and you use it to look the app up.
- **Client ID** is the app's public identifier (`Iv1.…` / `Iv23…`). It's what you put in the user-authorization URLs of Flow 2, and GitHub now recommends it as the issuer when signing the Flow 1 JWT (the App ID still works).
- **Installation ID** identifies *where* the app is installed. GitHub's resource API centers on this one, because that's where the actual authorization lives. For a single-enterprise automation, discover it once, put it in config, and leave it alone; it's stable for the life of the installation.

<Callout tone="tip">
  One app can have multiple installations with different permission grants at each. A token minted from installation A cannot touch resources of installation B.
</Callout>

### Permissions vs scopes

GitHub Apps use **fine-grained permissions**: resource-type-specific grants like `Enterprise teams (read)` or `Contents (write)`. OAuth Apps and classic PATs use **OAuth scopes**: broad categories like `repo` or `read:org`. These systems don't mix. A `ghs_` installation token has no concept of scopes. A `gho_` OAuth token has no concept of fine-grained permissions.

### Client secret

When creating a GitHub App you can skip the client secret entirely. The client secret only exists to support Flow 2 (user authorization). An app with no client secret cannot do Flow 2. For backend automations with no human in the loop, you don't need one.

## The two auth flows

That anatomy gives the app an identity, declared permissions, and an installation. What it still doesn't have is a token, and every API call needs one. Getting a token comes down to a single question: **is there a human in the loop?**

That splits cleanly into two flows, and which one you use decides which token you get.

- **Flow 1 (installation token).** The app authenticates as itself with its private key. This is the common case: CI pipelines, scheduled jobs, batch automation with no human present. Produces a `ghs_…` token.
- **Flow 2 (user access token).** The app authenticates on behalf of a specific person, with its client secret. Reach for this when a human starts the action: dashboards, CLI tools, bots that post as the user. Produces a `ghu_…` token.

The two sections below walk through each in turn.

## Flow 1: App acting as itself (installation token)

This is the flow you'll use most: an app running with no human attached. It proves it's itself by signing a short-lived JWT with its private key, trades that JWT for an installation token, and uses that token against the resource API. Three steps, shown in full below:

**Step 1: Generate a JWT.** Sign a JWT using your app's private key (RS256). Three payload fields, no more:

```python title="Generate a JWT (PyJWT)"
import time, jwt  # pip install PyJWT cryptography

now = int(time.time())
token = jwt.encode(
    {
        "iss": CLIENT_ID, # app's Client ID (App ID also works)
        "iat": now - 60,  # subtract 60s as a clock-skew buffer
        "exp": now + 600, # max 10 minutes
    },
    open("private-key.pem").read(),
    algorithm="RS256",
)
```

This JWT is only valid for the Apps API (`/app/...`). It cannot be used for repos, billing, or any resource endpoint.

**Step 2: Exchange for an installation access token.** The JWT only proves you're the app; it can't touch a single repo. Trade it at the installation's `/access_tokens` endpoint for a token scoped to what that installation was granted:

```python title="Exchange JWT for installation token"
import requests  # pip install requests

resp = requests.post(
    f"https://api.github.com/app/installations/{INSTALLATION_ID}/access_tokens",
    headers={
        "Authorization": f"Bearer {jwt_token}",
        "Accept": "application/vnd.github+json",
        "X-GitHub-Api-Version": "2022-11-28",
    },
)
installation_token = resp.json()["token"]  # ghs_…
```

You can optionally scope the token below what the installation was granted. Pass `repositories` or `repository_ids`, plus a narrower `permissions` map, in the request body. Different jobs, different access levels, same app.

<Expand title="Optional: request body scoping">
The body below limits a token to two specific repositories and a narrower permission set than the installation holds. Anything not listed, the token can't touch, even if the installation has broader access.

```json
{
  "repository_ids": [111222333, 444555666],
  "permissions": {
    "contents": "read",
    "pull_requests": "write"
  }
}
```

</Expand>

GitHub returns a `ghs_…` token valid for 1 hour.

**Step 3: Use the installation token.** Pass `ghs_…` as `Authorization: Bearer` on every resource API call. When it expires, restart from step 1.

<Callout tone="info">
  Each installation has its own rate limit bucket: 5,000 requests/hour. An app installed in three orgs gets 15,000 req/hr total with no sharing. That ceiling scales with your footprint. A service-account PAT is stuck with one bucket no matter how much you run through it.
</Callout>

Client libraries handle steps 1 and 2 automatically. You provide App ID, private key, and Installation ID; you get back an authenticated client that refreshes tokens internally. See [Client libraries](#client-libraries) below.

## Flow 2: App acting on behalf of a user (user access token)

For situations where a human is interacting with your app and it needs to act as them: dashboards, CLI tools, bots that post on a user's behalf. This flow uses the **Client ID and Client Secret**, not the private key. The private key is never involved.

<Callout tone="warning">
  The resulting <code>ghu_…</code> token is doubly constrained: by the app's installed permissions AND by what that specific user can access. It can never exceed either boundary, even if the user normally has broader access elsewhere.
</Callout>

### Web application flow

The standard browser-based path, for apps that can receive a redirect. The user bounces out to GitHub's authorization page and back to your callback, and you exchange the result for a token. Three steps:

1. **Redirect the user** to `https://github.com/login/oauth/authorize` with your Client ID. GitHub shows an authorization prompt.
2. **GitHub redirects back** to your callback URL with a short-lived `?code=` parameter.
3. **Exchange the code.** POST to `https://github.com/login/oauth/access_token` with your Client ID, Client Secret, and the code. You receive a `ghu_…` user access token, and optionally a `ghr_…` refresh token if you've enabled token expiry in your app settings.

<Callout tone="tip">
  Token expiry is opt-in in app settings. When enabled: user tokens last 8 hours, refresh tokens last 6 months. When disabled: user tokens have no expiry.
</Callout>

<Expand title="Optional: PKCE for public clients">
GitHub supports PKCE for this flow. Add `code_challenge` (base64url-encoded SHA-256 of a random `code_verifier`) and `code_challenge_method=S256` to the authorization URL, then include `code_verifier` in the token exchange. Required for SPAs and mobile apps where a client secret can't be stored safely. Optional but worthwhile for server-side apps too.
</Expand>

### Device flow

For CLIs and tools that can't open a browser or receive a redirect.

1. **Request a device code.** POST to `https://github.com/login/device/code` with your Client ID. GitHub returns a short `user_code` and a verification URL.
2. **Display the code.** Print the URL and `user_code`. The user visits that URL on any device and enters the code.
3. **Poll until authorized.** Repeatedly POST to `https://github.com/login/oauth/access_token` with your `client_id`, the `device_code` (not the `user_code`), and `grant_type=urn:ietf:params:oauth:grant-type:device_code`. GitHub returns `authorization_pending` until the user authorizes, then returns the `ghu_…` token.

## OAuth Apps, for contrast

OAuth Apps are an older, separate integration type. They're worth understanding because you'll run into them in the wild, and they look a lot like GitHub Apps from the outside. The GitHub CLI (`gh`) authenticates via an OAuth App, which is why `gh auth token` returns `gho_…` and `gh auth login --scopes` takes classic OAuth scopes. The differences in the table below are what matter.

| | GitHub App | OAuth App |
|:--|:--|:--|
| Identity | Own actor, appears as `app[bot]` in audit logs | Acts as the authorizing user |
| Access model | Fine-grained permissions per resource type | Classic OAuth scopes (`repo`, `read:org`, etc.) |
| Can act without a user | Yes, via Flow 1 (installation token) | No, always tied to a user |
| Token types | `ghs_…` or `ghu_…` | `gho_…` |
| Token lifespan | 1 hour (installation), configurable (user) | No expiry by default |
| Repo access control | Per-installation, repo-specific | All repos the user can access |
| Enterprise billing APIs | Supported (some gaps, improving) | Not supported |
| EMU support | Yes, enterprise apps fully supported | Restricted, must be enterprise-approved |

<Callout tone="warning">
  OAuth Apps are not a migration path from classic PATs. They carry many of the same limitations: user-tied, broad scopes, no expiry by default. GitHub Apps are the right destination.
</Callout>

## Client libraries

Those three steps in Flow 1 (generate a JWT, exchange it for an installation token, use the token) are what every major client library automates. You provide App ID, private key, and Installation ID; you get back an authenticated client that manages token refresh internally. You won't write that JWT code by hand in production.

**JavaScript / TypeScript:** [`@octokit/auth-app`](https://github.com/octokit/auth-app.js), [`@octokit/rest`](https://github.com/octokit/rest.js), [`octokit`](https://github.com/octokit/octokit.js)

The official GitHub client family. `@octokit/auth-app` handles the JWT exchange. Pass `appId`, `privateKey`, and `installationId`; installation tokens are minted and refreshed for you.

**Python:** [`PyGithub`](https://github.com/PyGithub/PyGithub), [`githubkit`](https://github.com/yanyongyu/githubkit)

`PyGithub` is the established library. `githubkit` is a newer alternative with better async support and full type annotations. Both accept the same three inputs for GitHub App auth.

**Go:** [`google/go-github`](https://github.com/google/go-github), [`palantir/go-githubapp`](https://github.com/palantir/go-githubapp)

`go-github` is the standard low-level REST client. `palantir/go-githubapp` builds on top for GitHub App-first use: webhook routing, installation client management, and token caching. It exposes three client types: app client (app metadata only), installation client (full API within granted permissions), and token client (static OAuth token).

**Ruby:** [`octokit.rb`](https://github.com/octokit/octokit.rb)

The official Ruby client. Supports GitHub App authentication the same way as the JS family.
