Every few weeks someone drops a graph in the incident channel: p99 latency, flat all day, then a cliff straight up at 5pm. The queries didn't change. The data didn't change. So what did?

Almost always, it's the **connection pool** — the part of the stack nobody looks at because it's working right up until it isn't.

## The mental model

A Postgres connection is expensive. Each one is a real OS process with its own memory. So you don't hand them out per-request; you keep a **pool** of them and lend them out. The trouble starts when more requests want a connection than the pool can offer.

<Callout tone="tip">
  The pool isn't a performance optimization you bolt on later. It's a queue. And like every queue, its behavior under load is the whole story.
</Callout>

When the pool is exhausted, new requests don't fail — they **wait**. That wait is invisible to your query timing and very visible to your users. Here's the part that bit us:

<Terminal filename="pgbouncer.ini" animate>

```ini
[databases]
app = host=10.0.0.5 port=5432 dbname=app

[pgbouncer]
; this single line cut our p99 in half
pool_mode = transaction
default_pool_size = 20
max_client_conn = 2000
```

</Terminal>

## Why transaction mode wins

In **session** mode, a client holds its server connection for the entire session — including the long stretches where it's doing nothing but thinking. In **transaction** mode, the connection goes back to the pool the instant a transaction commits. Same hardware, many times the throughput.

- Reads that were queuing now find a free connection immediately.
- Idle clients stop hoarding server processes.
- Your `default_pool_size` can stay small and sane.

> A healthy pool is mostly empty. If yours is always full, you don't have a tuning problem — you have a queueing problem wearing a tuning costume.

<Callout tone="warning">
  Transaction mode breaks features that rely on session state — `SET`, advisory locks, prepared statements without care. Read the [PgBouncer compatibility guide](https://www.pgbouncer.org/features.html) before you flip it in prod.
</Callout>

## The one-line fix, in context

We didn't add hardware. We didn't rewrite a single query. We changed `pool_mode` and watched the cliff flatten into a gentle hill. The system was never slow — it was just tangled, and one thread was all it took to loosen the knot.

Next time the graph spikes, don't start with the query plan. Start with the queue.
